# Політика завантаження, валідації та карантину (CityFlow S08, Лаба 2)

Реалізація: `src/lab02/validate.py` (правила), `src/lab02/ingest.py` (staging), `src/lab02/pipeline.py` (публікація).
Правила — навчальний контракт Лаби 2; універсального quality-framework немає.

## 1. Шари та рішення по рядках
- **stg** — оригінальні значення як `text` + `batch_id`, `source_file`, `source_row_number` (номер CSV-запису після заголовка), `loaded_at`. Кількість рядків = кількості CSV-записів, повтори включно.
- **core** — типізована перевірена копія: PK, FK, `NOT NULL`, `CHECK`. Публікується повним snapshot в одній транзакції.
- **audit** — `pipeline_runs`, `batch_sources` (SHA-256 файлів пакета), `row_decisions` (рішення по кожному CSV-запису), `run_file_stats`, `reconciliation`.
- Кожен CSV-запис має **один** фінальний статус: `accepted`, `rejected` або `duplicate`; головна причина — `reason_code`, усі причини й примітки нормалізації — `reason_codes`. Вихідний payload зберігається для `rejected`/`duplicate`; для `accepted` він лишається в staging (за `source_file` + `source_row_number`).
- Рядки з staging не видаляються. Якщо певного типу проблем у пакеті немає, лічильник не вигадується; правила демонструються на малих fixtures у `tests/lab02/test_validate.py`.

## 2. Типи та порожні значення
ID — `text`; кількість — `integer`; суми — `numeric(12,2)` (більше двох знаків округлюється half-up); час — `timestamptz`; прапорець — `boolean` (`true/false`, `t/f`, `1/0`).
Порожній ключ → `EMPTY_KEY`. Порожнє обов'язкове поле (ім'я, місто, назва, статус) → `MISSING_REQUIRED`. Порожній `phone` помилкою не є. Невідоме число нулем не підставляється.

## 3. Дати
- ISO 8601 із `Z` або зсувом (`+hh:mm`) → UTC.
- `DD/MM/YYYY HH:MM` → **явно UTC**, спочатку день, потім місяць (`04/09/2025 11:32` = 4 вересня 2025). Автовизначення day/month не застосовується.
- Частки секунди довші за мікросекунди **відкидаються** (truncate) у core; оригінал лишається в staging.
- ISO без зсуву, неможливі календарні дати та інші формати → `INVALID_DATE` (часовий пояс не вгадується).

## 4. Суми, валюти, категорії
- Валюти: `UAH`, `USD`, `EUR`. Дозволена нормалізація — лише обрізання пробілів по краях і верхній регістр. Код `UA H` **не виправляється**: `INVALID_CURRENCY`.
- `quantity` — ціле число `> 0` (`INVALID_QUANTITY`); суми `unit_price`, `line_discount`, `line_total`, `subtotal_amount`, `delivery_fee`, `discount_amount`, `total_amount` — `≥ 0` (`INVALID_AMOUNT`).
- Ціна товару: активний (`is_active = true`) із ціною `≤ 0` → `INVALID_PRICE`; для неактивного нуль допустимий; від'ємна ціна недопустима.
- Пробіли по краях текстових полів обрізаються для всіх файлів; рядок лишається `accepted` з приміткою `WHITESPACE_TRIMMED`.
- Email унікальним не оголошується (правила немає).

## 5. Повтори та конфлікти
Порівнюються всі бізнес-колонки після дозволеної нормалізації; `batch_id`, `loaded_at`, `source_row_number` у порівняння не входять.
- Усі копії однакові → перша лишається, решта `duplicate / FULL_DUPLICATE`.
- Однаковий ключ, різні значення, достовірної версії немає → вся група `rejected / KEY_CONFLICT` (останній рядок не обирається).

## 6. Зв'язки
Порядок: customers, merchants → products, orders → order_items. Батьком є лише **прийнятий** запис.
`ORPHAN_MERCHANT_FK` (товар/замовлення), `ORPHAN_CUSTOMER_FK`, `PARENT_REJECTED_ORDER`, `PARENT_REJECTED_PRODUCT` (позиція з відсутнім або відхиленим батьком). Якщо причин кілька, `reason_code` — перша за пріоритетом, решта — у `reason_codes`.
Наслідок: замовлення, усі позиції якого відхилено, лишається в core без позицій; це не помилка політики, а видима властивість пакета.

## 7. Публікація, повторний запуск, збої
1. `RUNNING` реєструється окремою транзакцією до публікації.
2. staging завантажується однією транзакцією (заголовок і довжина рядка перевіряються до `COPY`).
3. В одній транзакції: рішення → `audit.row_decisions`; `TRUNCATE core.order_items, core.orders, core.products, core.merchants, core.customers` (без `CASCADE`, `audit` не зачіпається); вставка п'яти таблиць; звірка; `SUCCESS`.
4. Звірка: `input = accepted + rejected + duplicate` для кожного файла; кількість і набір ключів `accepted` ↔ core (в обидва боки); суми й кількості `orders`/`order_items` окремо за валютою (staging-accepted ↔ core); відсутні FK = 0. Порушення зупиняє публікацію.
5. Помилка → `ROLLBACK`; `FAILED` із текстом помилки пишеться **окремою** транзакцією.
6. Повторний запуск того самого пакета не змінює бізнес-стан (повний snapshot), але створює новий `run_id`. Той самий `batch_id` із іншим вмістом файла відхиляється (SHA-256 у `audit.batch_sources`).
